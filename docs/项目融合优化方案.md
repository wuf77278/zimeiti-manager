# 项目融合优化方案

## 1. 背景

当前项目已经融合了多个来源：主应用的 React/FastAPI 诊断工作台、抖音本地素材分析原型、NoteRx 多 Agent 会诊框架，以及可选的 `social-auto-upload` 发布引擎。整体已经具备可运行基础，但融合后出现了几个典型问题：

- 诊断产品、运营发布台、第三方发布引擎混在同一套主服务中。
- `/api/ops/*`、Admin、发布任务、私信监控、Agent 执行等能力默认暴露，安全边界偏宽。
- 临时文件、构建产物、本地数据和第三方仓库容易混入主项目。
- README、环境变量、端口、产品命名存在不一致。
- MVP 的合规边界强调“用户自有数据诊断”，但代码中已包含真实发布和私信相关能力，需要显式隔离。

本方案目标不是砍掉融合进来的能力，而是将其分层、默认关闭、按需启用，使项目更安全、清晰、可交付。

## 2. 总体目标

将项目从“多个项目融合后的可运行状态”优化为：

1. **核心诊断产品清晰**：微信视频号与抖音诊断是主线能力。
2. **运营发布能力可控**：Ops、Admin、social-auto-upload、私信与 Agent 发布能力默认关闭，必须显式启用。
3. **目录结构干净**：临时文件、构建产物、第三方仓库、本地运行数据不进入主项目交付范围。
4. **配置口径统一**：README、`.env.example`、`start.sh`、Makefile、CI、FastAPI 元信息保持一致。
5. **上线风险降低**：默认不会暴露账号管理、发布执行、私信监控或外部 Agent 控制入口。

## 3. 优化原则

- **诊断主线优先**：任何优化都不能破坏微信视频号与抖音诊断流程。
- **危险能力默认关闭**：真实发布、账号操作、私信监控、Agent 控制接口必须显式启用。
- **本地数据不提交**：账号、素材、日志、临时视频、运行状态文件只存在本地。
- **第三方集成外部化**：`social-auto-upload` 作为可选外部依赖，不作为主项目源码的一部分。
- **先收边界，再清结构，最后提体验**：避免一开始大重构导致融合功能再次失控。

## 4. 模块边界设计

建议将项目能力分成三层。

### 4.1 内容诊断工作台，默认启用

这是主产品能力，默认启动后可用：

- 微信视频号内容诊断。
- 抖音素材/账号诊断。
- 截图与视频快识别。
- 多 Agent 会诊。
- 雷达图、建议、模拟评论、报告展示。
- 浏览器本地历史。

相关路径：

- `backend/app/api/diagnose.py`
- `backend/app/api/screenshot_api.py`
- `backend/app/platforms/douyin.py`
- `backend/app/platforms/wechat_channels.py`
- `frontend/src/utils/api.ts`

### 4.2 Ops 运营台，默认关闭

这是高级本地/内网能力，不应默认暴露：

- 账号管理。
- 素材管理。
- 草稿生成。
- 发布任务。
- Agent 发布计划。
- 私信监控。
- 账号指标采集。

相关路径：

- `backend/app/api/ops_api.py`
- `backend/app/ops/`
- `frontend/src/utils/opsApi.ts`
- `frontend/src/pages/OpsDashboard.tsx`

### 4.3 social-auto-upload，可选外部发布引擎

这是第三方发布能力，只在本地明确配置后启用：

- 抖音上传。
- 小红书上传。
- 平台登录态检查。
- 视频号当前不作为稳定自动上传能力。

相关路径：

- `backend/app/ops/social_auto_upload.py`
- `scripts/setup_social_auto_upload.sh`
- `docs/social-auto-upload-integration.md`

建议主项目不提交 `integrations/social-auto-upload/`，仅保留安装脚本和适配器。

## 5. 阶段一：收紧安全边界

### 5.1 默认关闭 Ops 接口

新增环境变量：

```env
OPS_ENABLED=false
OPS_ADMIN_TOKEN=
```

建议行为：

- `OPS_ENABLED=false` 时，不注册 `/api/ops/*`。
- `OPS_ENABLED=true` 时，所有 `/api/ops/*` 请求必须携带 token。
- token 建议通过 header 传递：

```http
Authorization: Bearer <OPS_ADMIN_TOKEN>
```

需要调整：

- `backend/app/api/routes.py`
- `backend/app/api/ops_api.py`
- `frontend/src/utils/opsApi.ts`
- `frontend/src/pages/OpsDashboard.tsx`

验收标准：

- 默认启动后 `/api/ops/state` 不可访问。
- 启用 `OPS_ENABLED=true` 且 token 正确后，Ops 接口可访问。
- 前端 Ops 页面在未启用时展示“运营台未启用”，而不是直接报错。

### 5.2 真实发布能力显式启用

当前发布模式由 `PUBLISHER_RUN_MODE` 控制。建议增加更明确的保护开关：

```env
PUBLISHER_RUN_MODE=dry_run
PUBLISHER_EXECUTION_ENABLED=false
SOCIAL_AUTO_UPLOAD_ENABLED=false
```

推荐模式语义：

| 模式 | 默认允许 | 行为 |
|---|---:|---|
| `dry_run` | 是 | 只模拟发布，不触达真实平台 |
| `browser_prepare` | 可选 | 打开平台工作台，不提交 |
| `upload_prepare` | 可选 | 准备上传与填写，不点击最终发布 |
| `social_auto_upload` | 否 | 调用本地 `sau`，可能真实上传 |

建议规则：

- 默认只允许 `dry_run`。
- `browser_prepare` 和 `upload_prepare` 需要 `PUBLISHER_EXECUTION_ENABLED=true`。
- `social_auto_upload` 需要同时满足：
  - `PUBLISHER_EXECUTION_ENABLED=true`
  - `SOCIAL_AUTO_UPLOAD_ENABLED=true`
  - `PUBLISHER_RUN_MODE=social_auto_upload`
- 真实执行前任务必须经过人工审核。

需要调整：

- `backend/app/ops/service.py`
- `backend/app/ops/social_auto_upload.py`
- `frontend/src/pages/OpsDashboard.tsx`

验收标准：

- 默认任何接口都不能真实上传。
- 误设 `PUBLISHER_RUN_MODE=social_auto_upload` 但未启用 `SOCIAL_AUTO_UPLOAD_ENABLED=true` 时，不会调用 `sau`。
- 执行真实上传前，前端和后端都能明确提示风险。

### 5.3 Admin 改为默认关闭与 token 鉴权

当前 Admin 面板使用硬编码 hash，并通过 query 传密码。建议改成：

```env
ADMIN_ENABLED=false
ADMIN_TOKEN=
```

请求方式：

```http
Authorization: Bearer <ADMIN_TOKEN>
```

需要调整：

- `backend/app/api/admin_api.py`
- `backend/app/main.py`

验收标准：

- 默认 `/admin` 不可访问。
- `/admin/api/stats` 未带 token 返回 401。
- token 不出现在 URL 中。
- 密钥不硬编码在代码里。

## 6. 阶段二：清理目录与融合残留

### 6.1 清理临时文件与构建产物

建议删除或移出以下内容：

```text
_tmp_local_home.png
_tmp_local_home_v2.png
_tmp_noterx_ref.png
tmp/*.log
tmp/*.pid
tmp/*.png
package-lock.json
```

说明：

- 根目录 `package-lock.json` 多余，实际前端 npm 项目位于 `frontend/`。
- 保留 `frontend/package-lock.json`。
- `tmp/`、`_tmp_*.png` 属于运行或截图临时产物。

### 6.2 更新 `.gitignore`

建议补充：

```gitignore
# Runtime temp
tmp/
_tmp_*.png
*.pid

# Ops local data
backend/data/ops_db.json
backend/data/ops_asset_uploads/
backend/data/temp_videos/

# Third-party local integration
integrations/social-auto-upload/
```

现有 ignore 已覆盖：

- `frontend/node_modules/`
- `frontend/dist/`
- `backend/venv/`
- `backend/data/*.db`
- `backend/data/noterx_workspace/`

建议继续保留。

### 6.3 外部化 social-auto-upload

保留：

```text
backend/app/ops/social_auto_upload.py
scripts/setup_social_auto_upload.sh
docs/social-auto-upload-integration.md
```

不提交：

```text
integrations/social-auto-upload/
```

推荐配置方式：

```env
SOCIAL_AUTO_UPLOAD_REPO_PATH=/Users/xxx/tools/social-auto-upload
SOCIAL_AUTO_UPLOAD_CLI=/Users/xxx/tools/social-auto-upload/.venv/bin/sau
```

验收标准：

- 未安装 `social-auto-upload` 时，诊断功能完全可用。
- Ops 页面显示发布引擎未安装，而不是启动失败。
- 主项目不依赖第三方仓库源码存在。

## 8. 阶段四：前后端结构优化

### 8.1 前端增加 Ops 可用性判断

建议增加前端环境变量：

```env
VITE_ENABLE_OPS=false
```

行为：

- `VITE_ENABLE_OPS=false` 时隐藏 Ops 入口。
- 如果用户直接访问 Ops 页面，展示“运营台未启用”。
- `VITE_ENABLE_OPS=true` 时，再请求 `/api/ops/runtime` 检查后端状态。

需要调整：

- `frontend/src/pages/OpsDashboard.tsx`
- `frontend/src/utils/opsApi.ts`
- 路由与导航入口。

### 8.2 后端 API 分层

建议逐步形成以下 API 分层：

```text
/api/diagnose/*      核心诊断
/api/screenshot/*    截图与视频快识别
/api/baseline/*      基线数据
/api/ops/*           可选运营台，默认关闭
/admin/*             可选 Admin，默认关闭
```

原则：

- 诊断 API 不依赖 Ops。
- Ops 关闭时，诊断测试仍能通过。
- Admin 关闭时，主服务仍能启动。

## 9. 阶段五：数据与隐私治理

### 9.1 明确数据分类

建议约定：

```text
backend/data/baseline.db              可重建基线数据
backend/data/ops_db.json              本地运营状态，不提交
backend/data/ops_asset_uploads/       用户上传素材，不提交
backend/data/temp_videos/             临时视频，不提交
backend/data/noterx_workspace/        本地记忆，不提交
```

文档需要说明：

- `baseline.db` 可通过 `make data` 重建。
- Ops 数据属于本地私有数据。
- 上传素材、账号状态、任务日志不应提交或公开同步。

### 9.2 上传文件安全限制

当前 Ops 素材上传已有扩展名和大小限制。建议继续补充：

- MIME 检查。
- 图片/视频实际格式探测。
- 上传目录固定在 `backend/data/ops_asset_uploads/`。
- 下载接口只允许 UUID 文件名。

验收标准：

- 无法上传 `.py`、`.html`、`.sh` 等文件。
- 无法通过路径穿越读取任意文件。
- 大文件超限后会删除半写入文件。

## 10. 阶段六：质量保障和交付流程

### 10.1 补充关键测试

建议新增或调整测试：

1. Ops 默认关闭测试。
2. Ops token 鉴权测试。
3. Admin 默认关闭测试。
4. Admin token 鉴权测试。
5. `social_auto_upload` 未显式启用时不能真实执行测试。
6. 诊断主线在 Ops 关闭时仍然可用测试。

建议测试命令：

```bash
make test
cd frontend && npx tsc --noEmit && npx vite build
make ci
```

### 10.2 CI 分层

当前 CI 已包含后端测试、前端 typecheck 和前端构建。建议后续拆分为：

```text
backend-core-tests
backend-ops-tests
frontend-build
```

Ops 测试可显式设置：

```bash
OPS_ENABLED=true
PUBLISHER_RUN_MODE=dry_run
```

验收标准：

- 诊断主线失败和 Ops 失败能独立定位。
- 默认 CI 不需要安装 `social-auto-upload`。

## 11. 推荐实施顺序

### 第一轮：安全和边界收紧

预计耗时：0.5～1 天。

任务：

1. 增加 `OPS_ENABLED`。
2. 增加 `OPS_ADMIN_TOKEN`。
3. 增加 `ADMIN_ENABLED` 和 `ADMIN_TOKEN`。
4. 给 `social_auto_upload` 增加二次开关。
5. 更新 `.env.example`。
6. 补充后端测试。

产出：

- 默认只能使用诊断主线。
- Ops、Admin、真实发布全部显式启用。

### 第二轮：目录清理与结构收敛

预计耗时：0.5～1 天。

任务：

1. 清理根目录临时文件。
2. 更新 `.gitignore`。
3. 移除根目录多余 `package-lock.json`。
4. 将 `integrations/social-auto-upload/` 作为外部可选依赖处理。
5. 统一端口和产品名。

产出：

- 项目目录干净。
- 新用户启动路径清晰。
- 主项目不携带第三方仓库和本地运行产物。

### 第三轮：文档和前端体验

预计耗时：1 天。

任务：

1. README 增加模块边界说明。
2. Ops 页面增加“未启用”状态。
3. social-auto-upload 未安装时展示安装指引。
4. Admin 文档改为 token 方式。
5. 补充本地数据落盘说明。

产出：

- 交付给他人时不容易误解项目能力。
- 用户不会误触真实发布能力。

### 第四轮：验证与交付

预计耗时：0.5 天。

任务：

1. 运行后端测试。
2. 运行前端 typecheck。
3. 运行前端 build。
4. 本地启动验证诊断主线。
5. 检查 Ops 默认关闭状态。
6. 检查 Admin 默认关闭状态。

产出：

- 主线稳定。
- 危险能力默认不可用。
- CI 可证明融合后没有破坏核心功能。

## 13. 最终建议

建议采用以下策略：

> 保留融合进来的能力，但默认关闭高级运营与真实发布能力；诊断是主产品，发布是本地高级功能。

这样既保留了项目融合带来的价值，又能避免项目变成边界不清、上线风险高、难以交付的大杂烩。

优先执行第一轮“安全和边界收紧”，因为它能最快降低风险，并且不会影响当前核心诊断功能。
